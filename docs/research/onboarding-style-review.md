# 온보딩 여행 스타일 분류 검토

| 항목 | 내용 |
|---|---|
| 대상 | PRD v0.5 미결 사항 1번이던 온보딩 제안안 (현재 PRD [5.1 FUNC-001-13](../PRD.md#51-회원관리-func-001)) |
| 결과 | **2026-10-26 수정 제안 그대로 채택** (스타일 7개, 1~3개 선택, 휴식 규칙). Notion 001-13·001-14, 디자인 03·13 반영 완료 |
| 질문 | 이 온보딩으로 사용자들의 여행 스타일을 빠짐없이 분류할 수 있는가 |
| 작성일 | 2026-10-26 |

## 결론

**대부분은 분류할 수 있지만, 지금 안 그대로는 "모든 사용자"를 분류하지 못합니다.** 한국인이 국내 여행에서 실제로 하는 주요 활동은 대부분 6개 스타일로 덮이지만, 빈틈이 셋 있습니다.

1. **축제·공연을 좋아하는 사용자를 나타낼 스타일이 없습니다.** 서비스의 핵심 콘텐츠(탐색 기본 탭이 축제)인데, TourAPI에서 축제는 별도 대분류(EV)라 6개 스타일 어디에도 연결되지 않습니다. 그대로 두면 취향 점수로 후보를 고르는 AI 추천(003-02)에서 축제가 모든 사용자에게 0점을 받습니다.
2. **"휴식"은 대응하는 장소 분류가 없습니다.** 다른 스타일은 TourAPI 대분류와 바로 연결되지만, 휴식은 장소 종류보다 여행 방식에 가까워 규칙을 따로 정해야 합니다.
3. **복수 선택에 제한이 없어 변별력이 떨어질 수 있습니다.** 6개를 모두 고른 사용자는 아무것도 고르지 않은 사용자와 구분되지 않습니다.

세 가지를 고치면 온보딩만으로 첫 추천에 필요한 수준의 분류는 됩니다. 온보딩은 처음 한 번의 출발점이고, 세밀한 취향은 행동 데이터(003-08)가 쌓이며 보정하는 구조이므로 온보딩이 모든 차원을 다 물을 필요는 없습니다.

**수정 제안**

| 항목 | 현재 제안 | 수정 제안 |
|---|---|---|
| 여행 스타일 선택지 | 휴식, 액티비티, 문화·역사, 미식, 자연, 쇼핑 (6개) | **축제·공연 추가 (7개)** |
| 선택 개수 | 제한 없음 | **1~3개** |
| 휴식 | 장소 분류로 매핑 | **장소 + 일정 방식 규칙**: 카페·찻집, 온천·스파 같은 휴양 장소에 가중치를 주고, 체류 시간을 늘리고 하루 장소 수를 줄임 |

## 근거 1. 실제 여행 활동과 비교 (포괄성)

국민여행조사(문화체육관광부·한국문화관광연구원)의 "여행지에서의 활동"과 6개 스타일을 맞춰 보면 다음과 같습니다. 수치는 2024년 1분기 잠정치입니다.

| 국민여행조사 활동 | 복수 응답 | 주된 활동 | 대응 스타일 |
|---|---|---|---|
| 자연 및 풍경 감상 | 77.4% | 41.5% | 자연 ✅ |
| 음식관광 | 65.1% | 12.8% | 미식 ✅ |
| 휴식/휴양 | 58.0% | 12.7% | 휴식 ✅ (장소 매핑은 근거 2 참고) |
| 가족/친지/친구 방문 | 18.4% | 14.1% | 해당 없음 (여행 코스 추천 대상이 아님) |
| 역사 유적지 방문 | 10.4% | — | 문화·역사 ✅ |
| 야외 위락 및 스포츠·레포츠 | — | 3.6% | 액티비티 ✅ |

- 상위 활동은 모두 스타일과 대응합니다. 특히 응답이 가장 많은 자연·음식·휴식 셋이 모두 들어 있습니다.
- 음식관광은 2025년 조사에서 65.6%로 전년보다 3.9%p 늘어 증가 폭이 가장 컸습니다. 미식을 별도 스타일로 두는 것이 맞습니다.
- 가족·친지 방문은 비율이 높지만 방문 목적이 정해진 여행이라 코스 추천의 취향 질문에는 넣지 않는 게 맞습니다.
- 축제·행사 참여 비율은 이번 자료에서 확인하지 못했습니다. 다만 축제는 이 서비스가 제공하는 핵심 콘텐츠라 사용자 비율과 상관없이 선호를 받아야 합니다(근거 2).

## 근거 2. 추천 데이터와 연결 (매핑 가능성)

AI 추천은 서버가 취향 점수로 후보를 고르고(003-02 1단계), 점수는 장소 분류별로 계산합니다(003-08). 따라서 **스타일 하나하나가 TourAPI 분류와 연결돼야** 실제로 추천에 영향을 줍니다.

TourAPI는 새 분류 체계(lclsSystm)를 쓰며, 대분류는 다음 10개입니다. 옛 분류(cat1~3)는 관광지의 31%만 채워져 있고 새 분류는 100% 채워져 있다는 개발 기록이 있어, 매핑은 새 분류로 해야 합니다.

| TourAPI 대분류 | 대응 스타일 | 판단 |
|---|---|---|
| NA 자연 | 자연 | ✅ 바로 연결 |
| HS 역사 | 문화·역사 | ✅ 바로 연결 |
| VE 문화관광 (전시·공연시설·전망대 등) | 문화·역사 (전시·공연), 자연 (전망) | ⚠️ 중분류별로 나눠 연결해야 함 |
| EX 체험 | 액티비티 | ✅ 바로 연결 |
| LS 레저스포츠 | 액티비티 | ✅ 바로 연결 |
| SH 쇼핑 | 쇼핑 | ✅ 바로 연결 |
| FD 음식 | 미식 (카페·찻집은 휴식에도) | ✅ 바로 연결 |
| **EV 축제/공연/행사** | **없음** | ❌ **빈틈** |
| AC 숙박 | 해당 없음 (숙소 추천 003-04에서 따로 처리) | — |
| C01 추천코스 | 해당 없음 | — |

- **축제(EV)가 빠지면 생기는 문제:** 축제 후보는 어떤 사용자의 취향 점수도 받지 못해 상위 40개 후보(003-02)에 들기 어렵습니다. 축제를 보러 온 사용자가 많을 서비스에서 축제가 추천에 잘 안 나오는 결과가 됩니다. "꼭 포함할 장소"로 직접 넣는 경우만 예외입니다.
- **휴식이 대분류와 바로 연결되지 않는 이유:** "카페·스파처럼 여유롭게"는 장소 종류(카페, 온천·스파)와 여행 방식(오래 머물기, 적게 이동하기)이 섞여 있습니다. 장소 가중치만 주면 효과가 약하므로, 페이스처럼 일정 방식에도 반영하는 규칙이 필요합니다.
- **레저스포츠 데이터 주의:** 옛 콘텐츠 타입 "레포츠(28)"로 분류된 장소의 59%가 새 분류에서는 숙박 > 캠핑이었다는 개발 기록이 있습니다. 액티비티 매핑은 옛 콘텐츠 타입이 아니라 새 분류(EX, LS)로 해야 합니다.

## 근거 3. 선택 방식 (변별력)

- 스타일은 서로 배타적인 유형이 아니라 **선호 묶음**입니다. 한 사용자가 여러 개를 고를 수 있어야 하는 건 맞습니다(디자인 예시도 3개 선택).
- 하지만 개수 제한이 없으면 "다 좋아요"를 고르는 사용자가 생기고, 이 경우 스타일 점수가 모두 같아져 추천에 아무 영향을 주지 못합니다.
- **1~3개로 제한**하면 사용자가 우선순위를 드러내게 되고, 7개 중 3개면 조합이 63가지(1개 7 + 2개 21 + 3개 35)라 사용자를 나누기에 충분합니다.

## 근거 4. 스타일 말고 다른 축은 충분한가

여행 스타일은 "어떤 곳을 좋아하는가" 한 축입니다. 사용자의 여행 방식을 나누는 나머지 축은 다른 질문과 데이터가 맡습니다.

| 축 | 어디서 받는가 | 판단 |
|---|---|---|
| 하루에 다니는 양 | 온보딩 페이스 | ✅ |
| 하루 시작 시간 | 온보딩 선호 시간대 | ✅ |
| 이동 부담 | 온보딩 이동 편의 | ✅ |
| 반려동물 | 온보딩 반려동물 | ✅ |
| 누구와 가는가 | 추천 요청의 동행 유형, 동행 유형별 프로필(003-08) | ✅ 온보딩에서 받지 않는 게 맞음 |
| 세부 취향 (박물관 vs 미술관 등) | 행동 데이터(003-08) | ✅ 관심 카테고리 질문을 빼도 됨 |
| 밤 일정 선호 | 없음 | ⚠️ 디자인에 "밤에 가기 좋은 곳" 칩이 있지만 취향으로는 받지 않음. 첫 버전은 축제(야간 행사 다수)와 행동 데이터로 대신하고, 필요하면 나중에 추가 |
| 실내·실외 | 장소의 실내·실외 구분(006-01) + 추천 요청의 "실내 위주로 짜기"(003-01) | ✅ 날씨·계절에 따라 매번 바뀌는 선호라 온보딩이 아니라 요청마다 받음. 스타일과도 겹침(자연·액티비티는 대부분 실외, 문화·쇼핑·미식은 대부분 실내) |
| 예산, 혼잡 회피 | 없음 | 첫 버전에서는 받지 않음. 데이터(요금·혼잡도)도 부족해 질문해도 추천에 반영하기 어려움 |
